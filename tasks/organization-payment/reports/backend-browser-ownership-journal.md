# Backend browser ownership journal hardening

Status: code/test-only increment complete; runtime acceptance remains gated.

## Implemented boundary

- `supervisor.json` is created once with an exact owner PID/start tick/nonce, session, canonical configuration binding, and a persisted journal binding.
- The journal is an append-only bounded generation chain rooted in the immutable claim binding. Each exclusive generation file and append-only head entry is flushed with `fsync`, carries its generation and previous digest, and records the full launch-intent stack plus each owned PID, creation tick, role, exact parent identity, executable, and session/config provenance. Recovery requires the exact contiguous chain, so a stale valid generation cannot replace the latest state silently.
- Journal integrity is a canonical SHA-256 corruption detector cross-bound to the immutable claim digest. It is deliberately not described as authentication: a party able to rewrite both local artifacts can recompute these unkeyed digests.
- Recovery is a callable imported flow (`recover`) and requires both an exact latest `{generation, digest}` anchor retained independently by its coordinator and a reloadable publisher interface before it hydrates state or starts a helper. The supplied anchor must equal the value reopened from that interface. Claim/journal/config/tool/no-intent validation is completed without `Popen`; only then is a distinct recovery-hydrated state installed so its bounded process snapshot uses `intent_only` and publishes before helper spawn. Helper transport, timeout, exit, stderr, UTF-8, or interruption failure retains the helper intent/handle. By contrast, JSON/schema or later lineage semantics fail after a valid helper result has cleared its intent and advanced the anchor; the safe wrapper invalidates that hydrated state without cleanup, and retry must use the newly reopened coordinator anchor. Cleanup is not attempted until ownership validation completes. Recovery refuses stale-prefix rollback, active-owner, session, tick, parent, executable, config, tool-content, malformed/truncated, duplicate PID/role, incomplete-pair, and unresolved-launch-intent mismatches.
- `WindowsRun` construction remains side-effect-free and may omit a publisher for inspection, but `claim()` requires a callable, reloadable coordinator-owned anchor publisher before creating claim/journal artifacts or allowing any managed spawn. Every durable generation publishes a fresh strict copy of `{generation, digest}` in order, then immediately reopens, validates, and exact-compares the publisher's anchor before returning. A no-op, stale, conflicting, malformed, or unreadable acknowledgement therefore fails closed; for launch intents that failure occurs before the managed `Popen`. Callback mutation cannot alter supervisor state. Because a publisher may durably store and then raise, recovery never infers whether the external anchor stayed old or advanced: it reopens the publisher and reconciles that exact value against the journal. No anchor is persisted beside the journal and no digest or secret is logged.
- Process-launch tracking is an explicit three-policy boundary with a closed phase/role matrix validated before journal mutation or `Popen`: only pre-claim `untracked/helper`, post-claim `intent_only/helper`, and post-claim `owned/command|browser_launcher` are permitted. Managed PHP/Node commands use `owned` and require exact PID/start-tick registration. A PowerShell helper after claim uses `intent_only`: its durable/published helper intent exists before `Popen`, identity and descendant discovery are deliberately skipped to avoid recursion, and the intent is cleared/published only after bounded exit, zero status, empty stderr, bounded stdout, and successful UTF-8 decoding. Timeout, bad output, process error, exception, or interruption before that validation retains the handle and unresolved intent, so recovery refuses `recovery_incomplete`. If publishing the later clear fails, the external anchor may still be prior or may already be advanced; the mandatory reopen determines whether recovery rejects stale anchoring or evaluates the advanced durable state. Pre-claim PowerShell inspection remains explicitly `untracked`; it is bootstrap-only and the runtime entrypoint remains gated.
- Intent clearing is conservative in memory: any `BaseException` while persisting or publishing a clear restores the exact popped intent. A later generation therefore re-states unresolved work instead of silently publishing an empty in-memory stack. If the clear reached the publisher before it raised, a new instance may instead observe that advanced anchor; the required reopen step determines which durable state is authoritative.
- The managed lifecycle has an explicit phase boundary. Direct PHP/TLS launch and public harness, ownership-assertion, and run-code paths require a fresh normal claimed phase; pre-claim, claim-failed, recovery-hydrated, closed, and invalidated states refuse before any launch intent or `Popen`. Recovery cleanup remains separate and cannot reuse those normal-run paths.
- Journal deletion is gated by a private monotonic state reached only after exact `integrity-post` evidence validates, followed by an exact cleanup with no listener, live owned identity, or uncertainty. Before the first unlink it revalidates the full chain against the supervisor's latest live/published anchor; stale-prefix rollback therefore retains the claim, head, and remaining generations and makes cleanup uncertain. Public `postcheck_complete` mutation, failed/partial cleanup, and interrupted/incomplete runs retain the journal and invalidate the run.

## Residual gate

This increment does not authorize the disabled runtime entrypoint or establish browser acceptance. The publisher is mandatory at claim, but the current disabled runner still has no reviewed coordinator implementation, so it cannot claim or spawn; standalone crash recovery is not claimed and remains gated. Managed PHP/TLS, browser launcher, harness/run-code commands, and close CLI are exact-owned after claim. Post-claim PowerShell helpers are not claimed as exact-owned or recoverable by PID: they are intent-only, and any incomplete helper forces the operator/recovery gate instead of guessed adoption. Pre-claim PowerShell helpers remain untracked bootstrap operations behind the disabled runtime boundary. A crash after any managed spawn begins but before exact registration or validated helper completion leaves a persisted launch intent and recovery fails closed with `recovery_incomplete`; an operator must resolve that host state under a separately reviewed process-ownership procedure. The unkeyed chain plus independent anchor detects local corruption and stale-prefix replacement under the stated artifact model but does not authenticate against an actor able to rewrite both local artifacts and the external anchor. Real Windows process lineage, coordinator integration, append/fsync behavior, helper-process failure behavior, and cleanup must still be validated in the reviewed isolated manifest environment before P17c can be accepted.
