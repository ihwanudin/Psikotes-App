## 1. Scope, authority, and safety boundary

This document specifies a **PAPI-first** participant journey from the existing lobby through fixed-order forced choice and into a blocked result-pending destination. It applies the accepted generic session lifecycle to the recommended first thin slice; it does not define one universal interaction renderer for every generic instrument. It does not authorize routes, DTOs, instrument content, scoring, or production activation.

The Q0/S0/S1 question and answer behavior in this version applies only to the future PAPI slice. RMIB ranking requires a separately frozen, keyboard-equivalent unique-ranking interaction; Kraepelin requires a separately frozen timed grid, seeded generation, and event-ingest/offline contract; IST requires separately frozen subtest, asset, and ME two-timer behavior. None may inherit PAPI radio semantics by default. All remain blocked by their respective authority and HTTP gates. DASS-21 remains a separate lifecycle, storage, consent, scoring, and retention lane and is never part of this generic session slice.

All question, option, and instruction copy below is synthetic structure-only content. It must be replaced by a licensed, approved, versioned participant projection before any instrument is reachable. PAPI and IST remain import-not-ready and start-not-ready under their authority packs. No example in these artifacts is a real question, answer key, dimension, score, interpretation, or administration rule.

The stable session authority used here is limited to the canonical lifecycle and error semantics in `API_CONTRACT.md` and `tasks/handoffs/f2-assessment-session-contract.md`. The result-read consumer/DTO contract is not frozen. Therefore result fields, result availability, processing detail, report links, recommendations, and all post-submit copy are explicitly **provisional and blocked**.

## 2. Experience principles

1. **Server state wins.** The browser displays the server deadline and accepted answer revision; local time, animation, connectivity, or navigation never grants permission to write.
2. **One clear next action.** Each view has one primary action, with recovery actions subordinate and destructive submission separated.
3. **Progress is honest.** `saving`, `saved`, `offline/retrying`, `conflict`, `closed`, and `processing` are distinct text-and-icon states. Selection is never described as saved before an accepted receipt.
4. **No hidden loss.** Navigation waits for an accepted receipt or authoritative reconciliation. A participant can recover from interruption without silently overwriting a newer answer.
5. **Content stays protected.** The PAPI-first UI renders only the current participant-safe PAPI item projection. It never embeds scoring keys, dimensions, source paths, unrestricted definitions, or hidden future questions.
6. **Access is equivalent.** Keyboard, screen reader, touch, zoom, reflow, reduced motion, and poor-connection paths support the same completion outcome.

## 3. State and transition map

```text
Lobby
  | ready item selected                       | active item reopened
  v                                           v
Pre-start instructions -- sole Mulai ------> Opening / authoritative read
  | authority unavailable                     | new or replayed in_progress
  v                                           v
Authority blocked                         PAPI active question <---- authoritative refresh ---- Conflict
  | select                                   ^       |
  v                                          |       | reconcile / retry
Saving -------- accepted receipt ------------+-------+
  | transport unavailable
  v
Offline / retrying ---- connectivity + accepted receipt ----> PAPI active question

PAPI active question -- participant confirms submit --> Submitting / processing
PAPI active question -- server deadline or closed response -------> Deadline / closed
Saving/offline/conflict -- server deadline or closed response -> Deadline / closed

Submitting / processing -- stable submit response --> Result pending [PROVISIONAL/BLOCKED]
Submitting / processing -- recoverable failure ----> Submit recovery
Submitting / processing -- deadline/closed --------> Deadline / closed

Authority blocked -- return + authoritative lobby read --> Lobby
Result pending -- return + authoritative lobby read ----> Lobby
Deadline / closed -- return + authoritative lobby read --> Lobby
```

Back, reload, tab visibility changes, and reconnect always re-read authoritative state. They do not restart or extend the session.

Messages are examples of safe intent, not frozen product copy. Preserve stable machine codes for behavior; never display raw exceptions or SQL details.

## 6. PAPI-first content model

The Q0 renderer supports only an eventual participant-safe PAPI projection. It needs, at minimum, approved semantics for the current position, current prompt/legend, fixed ordered choices, selected value, navigation writability, and definition identity. Exact field names remain the API owner’s responsibility and are not frozen here.

Synthetic structure example:

> Question placeholder [position] of [total supplied by server]
>
> Choose the statement that fits the practice scenario best.
>
> Placeholder option one
>
> Placeholder option two

This example intentionally has no scoring meaning and must never enter a production definition. The UI must not infer PAPI duration/subtests. It also must not reuse this PAPI content model for IST, RMIB, or Kraepelin; their participant projections and interaction acceptance require separate, authority-backed artifacts.

## 7. Timer, persistence, and navigation rules

- Display time derives from `server_time`, `ends_at`/`write_deadline`, and a measured local offset. Resynchronize after start, resume/read, accepted autosave, and submit recovery.
- Announce named thresholds only (for example, a future approved warning threshold), never each second. Threshold values must be product-approved; none are frozen here.
- At displayed zero, immediately prevent new choices/writes and check server state. Only the server can confirm whether a receipt was on time.
- Maintain one answer request in flight and at most one coalesced latest pending selection in memory for the same tab. Do not persist sensitive responses to `localStorage` or IndexedDB without a separate security/retention decision.
- Reuse a mutation ID only for a byte-equivalent retry. Advance the revision only after an accepted receipt. A changed selection is a new logical mutation after reconciliation.
- Browser back/reload from an active route returns through I0 authoritative read and then directly to Q0; it does not construct a session from client storage or show pre-start instructions while time runs.
- Do not advance to another item until the current answer has an accepted receipt or the authoritative resume/read proves the value already exists.
- Submission seals answers. Canceling U0 restores focus to the submit trigger; successful submit moves to R0 without exposing an invented result.
